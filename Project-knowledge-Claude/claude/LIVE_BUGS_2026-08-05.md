## 1 — Cannot post. NOT SOLVED. Intermittent, and currently unmeasurable.

### What was measured (2026-08-05 ~02:30 UTC)

| Check | Result |
|---|---|
| Last successful post | **04 Aug 18:27 UTC**, then nothing for ~8h |
| Postgres logs — RLS violations / constraint errors | **none** |
| Edge function logs — any 4xx/5xx | **none in the retained window** |
| `s3-presign-upload` probed live with the owner's own token | **HTTP 200**, both `uploadUrl` and `pair.uploadUrl` returned |
| The actual `PUT` to storage with a 26-byte blob | **HTTP 200** |

So the upload path was **healthy at the moment of testing**. The fault is
**intermittent**. Poking at it after the fact will never catch it — which is the
whole reason the owner is angry, and he is right to be.

### The strongest hypothesis, from the codebase's own comments

`src/lib/s3Upload.ts` already carries retry-with-backoff specifically for
`FunctionsFetchError`, and `uploadPairToS3`'s doc comment says the single paired
presign exists *"to prevent the s3-presign-upload boot/shutdown thrash that
surfaces as FunctionsFetchError."*

That is an **edge-function cold-start failure**: intermittent by nature, worse
under concurrent load, invisible afterwards. It matches "many members all day,
fine when you check later" exactly.

### Why the member sees "Unknown error"

`WallPosts.tsx` `createPost()` ends in:

```ts
const msg: string = err?.message || "Unknown error";
```

"Unknown error" therefore appears **only when the thrown value has no
`.message`** — so the real cause never reaches the member, the owner, or the
logs. Every throw inside `s3Upload.ts` is a proper `Error`, so whatever is
escaping is NOT coming from there — it is something further out (an aborted
fetch, a DOMException, a non-Error rejection). **This is unresolved and must not
be guessed at.** Instrument first (§5), then read real rows.

**Do not "fix" this by widening the message string.** That hides it again.

## 2 — "0+ downloads" on Play. Not a code defect.

That number is Play's own aggregate on the public listing, published in coarse
buckets on Google's refresh schedule. It is not read from the app, the build, or
anything in this repo. The real install count is **Play Console → Statistics**,
which no session here can reach. No authoritative source was found for the exact
refresh delay, so **do not quote the owner a number.**

## 3 — Feed hides the newest posts. THIS ONE IS OUR REGRESSION.

Migration `20260804090000_feed_reshuffle_on_refresh.sql` contains, in our own
words:

```
-- No recency term: the owner wants maximum visibility of ALL posts, not the newest.
ORDER BY COALESCE(imp.viewers, 0) + random() * 6.0 ASC
```

That reading of his earlier instruction (*"maximum visibiltiy of all posts not
newer one"*) was **wrong**. His policy is BOTH: a new post must get maximum
views, AND the feed must reshuffle so older under-seen posts still surface. We
implemented the second at the total cost of the first — a post one minute old
competes on identical terms with one from June.

**The fix (designed, NOT yet applied):** a decaying freshness boost in tier 1 —
new posts sit on top for their first hours, then blend into the fairness pool;
the shuffle stays. Rehearse it and **show the owner the real before/after
ordering** before applying.

**No Android build is needed.** `get_broadcast_feed` is a database function; it
reaches every installed build the moment it is applied. Say this plainly — it is
the one piece of good news in this list.

## 5 — ⚠️ THE REAL DEFECT: nothing measures any of this

There is **no client error reporting of any kind** on this platform. A failed
post, a failed reply, a blank boot — all die silently in the member's browser.
The only signal is a member complaining to the owner, hours later, with no
detail. That is why every one of these reports ends in "I can't check", and
"I can't check" is not an answer.

### What to build — the agreed shape

1. **`client_errors` table** — `id, created_at, user_id, kind, message, detail
   jsonb, platform, app_build, url`. `kind` ∈ `post_create | reply | upload |
   blank_page`.
2. **`log_client_error(...)`** — SECURITY DEFINER, callable by `authenticated`
   (and `anon` for blank-page boots), **rate-limited per user** so it cannot be
   turned into a write amplifier, and RLS so no member can read anyone's rows.
3. **Wire three call sites:** the `createPost` catch (record what the error
   ACTUALLY was, not `"Unknown error"`), the reply failure path, and the app's
   top-level error boundary.
4. **An admin read** — failures per hour, grouped by `kind` and `app_build`.

**Honest split, state it to the owner every time:**

- the table + function are **DB-side → live immediately, no build, no deploy**;
- the **web** call sites go live ~90 seconds after merge;
- the **installed app only starts reporting after the next Android build.**

Until step 4 produces rows, any claim about the cause of #1, #4 or #5 is a guess.
