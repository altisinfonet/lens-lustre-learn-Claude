### Bug 1 — deleted account stayed signed in
Two defects, both in `src/hooks/core/useAuth.tsx`:
- `checkRestricted` had `if (error || !data) return false;` — it treated **"the
  profile row is gone"** the same as **"the lookup failed"** and kept the member
  signed in. Now split: `error` keeps them in, `!data` signs them out.
- The realtime guard subscribed to `event: "UPDATE"` only, so it was **blind to
  DELETE**. Now `event: "*"` with a DELETE branch.

Verified before changing: `supabase_realtime` has `pubdelete = true` and
publishes `profiles`; `profiles` has **REPLICA IDENTITY FULL**, so a DELETE
carries every column and the `id` filter matches. **Without those two facts the
fix would have silently done nothing.**

Code `AUTH-1005`. 7 pins in
`src/hooks/core/__tests__/deletedAccountSignOut.test.ts`, all 7 fail against the
old code.

**Measured, so nobody re-litigates it:** the deletion itself always worked —
`auth.users` and `profiles` both returned 0 rows, and there were **0 orphaned
comments table-wide**. The purge is thorough. Only the session never found out.

### Bug 2 — member list not live
`src/components/admin/AdminUsers.tsx`. The realtime subscription was always
correct. `scheduleRefresh` returned early when `activeQueryRef.current` was
null — and that ref is only set inside `fetchUsers`, which was **only ever
called from a click or the Enter key. Nothing loaded the list on mount.** So on
a freshly opened screen every live event was discarded. Fixed by loading on
mount. Code `ADMIN-8107`, 3 pins.

### Bug 3 — perceived delay ← **THE ONLY UNFIXED BUG**
**Located precisely. `src/App.tsx:180`:**
```ts
staleTime: 5 * 60 * 1000,      // data considered fresh for 5 minutes
refetchOnWindowFocus: false,   // returning to the app refetches nothing
```
**Likes and comments are NOT the problem** — both already have optimistic paths
(`usePostReactionMutations` has `onMutate` + `onError` rollback). What the owner
feels is these two settings: come back to the app and nothing refreshes;
navigate back to a screen and it serves data up to five minutes old.

**The fix is `refetchOnWindowFocus: true`**, possibly with a shorter `staleTime`
on feed queries. **NOT shipped** because it changes fetch behaviour for every
member on every screen against a free-tier database, and the previous session
had no capacity left to watch it live or revert. **Do this early in a session,
watch the feed, be ready to revert.**

### Bug 4 — could not post
`src/lib/fileSecurityScanner.ts:78` had `reader.onerror = reject`, which hands
reject the **DOM Event** and discards `reader.error` — the DOMException whose
name IS the cause. That is why the member saw
`non-Error thrown: {"isTrusted":true}` and why it was undiagnosable.

**Measured in production:** 26 failures, **100% `platform: app`, 0 from web**,
two real members — Mainak Mridha (23 attempts in one morning) and Shadequl Islam
(3).

Fixed twice over:
1. `FILE-5007` captures exception name, file, size, MIME, stage, duration,
   Android version, device model, viewport.
2. **Read-once refactor**: the photo is converted to stable in-memory bytes at
   selection (`src/lib/fileFromDataUrl.ts`) and every later step — scan,
   compression, thumbnail, upload — uses those. The original Android handle was
   previously read **up to five times**; now once.

**4b remains open:** which DOMException. **It needs one more failure on 1054 to
name itself.** Then check Admin → Error Log for `FILE-5007`.

## 4. HOW TO WORK HERE — the rules that are not negotiable

- ❌ No guesswork, assumptions, hidden operations, bulk modifications, auto-fix,
  "probably safe" logic.
- **Builds are cut only on his explicit GO.** A push to `main` deploys to
  members in ~90 seconds — treat that as needing GO too.
- Play "What's new" is **exactly** `Bug fixes and improvements.` The detailed
  changelog goes ONLY in `ANDROID_BUILD_TRIGGER`, newest at the top.
- **A Completion Verification Report after EVERY task** — ✅/❌/⚠️/N/A with
  concrete evidence. Never just "Done".
- **Enterprise structured logging on every function you write or modify.**
- **Never log a member's own words** — comment text, search terms, captions.
  Length, count or boolean only. `redact()` does NOT cover this: it drops keys
  that look like secrets, and `content` does not.
- **Never delete users. Never enter credentials. Never commit secrets.**
- **A post REQUIRES a photo; the caption is optional. A missing profile photo
  NEVER blocks posting, commenting or reacting.** Two separate rules, conflated
  once before.
- **Never show an invented value. Blank is honest.**
- Regression tests must fail against `main` first. If they pass there, delete them.
- **Bump `__APP_BUILD` in `src/main.tsx` on every web release** — currently
  `2026-08-06-8`. It is the only way to prove a deploy landed.

## 5. MECHANICS — how to actually ship here

**`git push` is BLOCKED** (proxy 403, deterministic — do not retry).
Push through the **GitHub Upload-files page**:

1. Copy files to `/mnt/user-data/outputs/<dir>/` (the upload tool rejects other paths).
2. Navigate to `github.com/altisinfonet/lens-lustre-learn-Claude/upload/main/<directory>`.
3. `find` the file input → `mcp__claude-in-chrome__file_upload`.
4. **WAIT ~5 SECONDS** after the upload before touching the form.
5. Set the commit message with the **native `HTMLInputElement` value setter**
   (typing does not register).
6. Click Commit **via JavaScript**, not coordinates — the page scrolls between
   the screenshot and the click, so coordinate clicks land in the description box:
   `[...document.querySelectorAll('button[type="submit"]')].find(b => b.textContent.trim() === 'Commit changes').click()`
7. **BYTE-DIFF EVERY FILE:** `git show origin/main:<path> | diff - <path>`.

**Hard-won rules:**
- **THREE FILES PER COMMIT. SIX FAILS** — a 6-file upload landed on a GitHub
  error page with no commit created.
- **One directory per commit** — the upload page is per-directory.
- **A commit can silently NOT happen.** Clicking Commit is not evidence it
  committed. Only the byte-diff is.
- **Deploys queue.** After several commits the marker reads the OLD value for a
  few minutes. Wait and re-check before concluding a deploy failed.
- **Verify in the ROUTE CHUNK, not just `index-*.js`.** Route code is in lazy
  chunks (`WallPosts-*.js`, `AdminUsers-*.js`). Checking only the entry gives
  false negatives.
- **The sandbox cannot reach production web — verify through the owner's
  browser**, reading values live off `window`.
- **The Chrome bridge can drop its tab group.** Stop after three failures, say
  so, and ask. If several browsers are connected you MUST ask which one.
- Sandbox starts empty: `git clone` works, **`npm ci` does NOT** (use
  `npm install`), `git push` is blocked.

**Cutting an Android build:** edit ONLY `ANDROID_BUILD_TRIGGER` (newest entry at
the top) and push it — that fires exactly one run.
**versionCode = 1000 + run_number.** Last run was #54 → 1054, so the next is
#55 → 1055.

**Supabase SQL editor** is Monaco:
`window.monaco.editor.getModels()[0].setValue(sql)` then click Run.
**Destructive statements open a confirmation dialog — clicking Run is not
enough. Always screenshot the result.**
