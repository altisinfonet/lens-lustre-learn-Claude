# The Android notification icon — why it was a white square, and how it is fixed

> Written 2026-08-02, after Android builds 1039, 1040 and 1041.
> Everything here was measured or read out of a real build log. Nothing is inferred.
>
> **2026-08-03 status:** carried unchanged through builds 1042, 1043 and 1044 —
> the in-bundle assertion (step below) ran and passed on every one. **1043 is
> live on Play (owner uploaded it 2026-08-03), so members' installed app now has
> this icon.** No drawable or workflow change is pending.

---

## 1. The symptom

Every push notification arrived with a **blank white square** in the status bar
instead of any mark. Reported by the owner with screenshots, 2026-08-02.

## 2. The cause — one sentence

**Nothing was configured, and Android's fallback is worse than nothing.**

Audited across the whole repository before touching anything:

| Checked | Found |
|---|---|
| `com.google.firebase.messaging.default_notification_icon` | **absent everywhere** |
| `com.google.firebase.messaging.default_notification_color` | **absent everywhere** |
| `com.google.firebase.messaging.default_notification_channel_id` | absent |
| an `ic_notification` drawable | **did not exist** |
| a notification channel created by the app | none |
| what the workflow injected into the manifest | only the OAuth intent-filter |
| what `@capacitor/assets` generates | launcher + splash **only** — never a notification icon |
| what `send-push` sends | `notification{title,body}` + `android{priority:high}`, **no icon** |
| `google-services.json` | present and correctly placed |

With no small icon declared, the messaging library falls back to the **launcher
icon**. And since API 21 Android **flattens the small icon to its alpha mask** —
it keeps only *which pixels are opaque* and throws every colour away, then paints
that shape in one flat colour.

The launcher icon is a fully opaque square. Its alpha mask is therefore a solid
rectangle. **That is the white square.** The image was never corrupt, and no
amount of re-exporting the launcher icon would have changed it.

> `send-push` sending no icon is **correct**. The manifest default is the right
> place for it — putting it in the payload would only cover pushes that go
> through that one function.

## 3. What was built

### The drawable

`resources/android/notification/ic_notification-{mdpi,hdpi,xhdpi,xxhdpi,xxxhdpi}.png`
— committed to the repo, **24 dp** at each density: **24 / 36 / 48 / 72 / 96 px**.

Every file must satisfy, and is checked before every commit:

- mode `RGBA`
- corner alpha `0` (transparent background)
- **zero non-white opaque pixels** — the mask is all that survives, so colour is
  wasted bytes and a lie about what will render

### The build step

The native `android/` folder is regenerated by `npx cap add android` on every
run and is **not** in the repo, so the icon cannot live there. The workflow step
`Install monochrome notification icon and manifest meta-data` runs **after
`npx cap sync android`** and:

1. copies each density into `android/app/src/main/res/drawable-<d>/ic_notification.png`
2. writes `res/values/notification_colors.xml` with
   `<color name="notification_accent">#C6A04A</color>`
3. inserts before `</application>`, after asserting the entries are **absent**
   and that there is **exactly one** `</application>`:

```xml
<meta-data android:name="com.google.firebase.messaging.default_notification_icon"
           android:resource="@drawable/ic_notification" />
<meta-data android:name="com.google.firebase.messaging.default_notification_color"
           android:resource="@color/notification_accent" />
```

4. ends with `ls -1` over the drawables and `grep -c default_notification` over
   the manifest, so the build log proves both landed.

### The bundle-level assertion — the part that matters most

The step above proves the files were *copied in*. It does **not** prove they
reach the shipped artifact, because the release build runs
`minifyEnabled true`, `shrinkResources true` and
`android.r8.optimizedResourceShrinking=true`. **A drawable referenced only from
the manifest is exactly the kind of resource a shrinker can drop**, and resource
optimisation is also free to rename the file path.

So a second step, `Prove the notification icon is actually inside the bundle`,
opens the built `.aab` and **fails the build** unless all three hold:

| Assertion | Why this form |
|---|---|
| `ic_notification` appears in `base/resources.pb` | the resource **table** — survives path renaming; a filename grep would not |
| `default_notification_icon` in `base/manifest/AndroidManifest.xml` | the bundled manifest is protobuf; the attribute names are plain UTF-8 inside it |
| `default_notification_color` in the same | same |

**Mutation-checked before committing** against three synthetic bundles: green on
a complete one, red with the drawable removed, red with the meta-data removed.

A future change that quietly strips the icon now stops at CI instead of shipping
another white square to the store. **This assertion runs on every single build**
— it is not a one-off check; 1042–1044 each passed it.

## 4. The design decision — and the mistake I made judging it

Three marks were shipped in one day:

| Build | Mark | Verdict |
|---|---|---|
| 1039 | drawn aperture, six wide wedges | **wrong** — reads as a flower at real size |
| 1040 | classic iris, six thin tangent cuts | legible, but not the owner's logo |
| **1041** | **the owner's logo, silhouetted** | **shipped — owner's decision** |

**My error, recorded so it is not repeated:** I evaluated every candidate at
**24 px** and told the owner his logo could not work. 24 px is the **1x (mdpi)**
case, and almost no phone in use today is 1x. A normal modern phone is **3x or
4x**, so the 24 dp icon is drawn at **72 or 96 physical pixels** — where the
badge *is* legible. Showing only the worst case was misleading, and the owner
was right to push back.

**1041 is cut five separate times, tuned per density**, rather than one image
resized five times, because the trade-off differs at every size:

| density | px | luminance threshold | thickening |
|---|---|---|---|
| xxxhdpi | 96 | 118 | none — keeps the most detail |
| xxhdpi | 72 | 120 | 1 |
| xhdpi | 48 | 128 | 2 |
| hdpi | 36 | 136 | 3 |
| mdpi | 24 | 140 | 4 — hairlines would otherwise vanish |

Source artwork: the logo PNG the owner supplied directly (256×256 RGBA with a
real alpha channel), **not** `resources/icon.png`. The silhouette is the bright
artwork of the badge — outer ring, the `5`, the aperture, the eye — as one shape.

Honest limit: at 1x it reduces to a ring and an eye. That density is rare.

> An earlier attempt derived a silhouette from `resources/icon.png` by luminance
> threshold with no per-density tuning and no thickening. It produced an
> illegible blob. **Thresholding alone is not enough** — thin strokes must be
> dilated *before* downscaling and the result hardened *after*, or they dissolve.

## 6. If it ever looks wrong again

1. **Is it a white square?** → the meta-data or the drawable is missing. The
   build would have failed, so check that the *installed* build is new enough
   (1041+; the first build members actually got is **1043**). An older APK on
   the handset shows the old behaviour.
2. **Is it a blurred blob?** → the drawable is present but the artwork is too
   fine for that density. Re-cut with more thickening for the low densities.
   Do **not** just resize one image.
3. **Is it the right shape but the wrong colour?** → that is not a bug. Android
   paints the mask; the shade tints it with `notification_accent`. You cannot
   ship a multi-colour status-bar icon, for any app.
4. **Changing the mark** is five PNG files in `resources/android/notification/`
   plus a build. No workflow edit, no code change. Upload them through GitHub's
   **Add file → Upload files** page (route A in the runbook) — exact bytes.
