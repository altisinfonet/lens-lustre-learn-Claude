### DEFECT FOUND BY RUNNING THE FLOW — AND IT IS A PRODUCTION DEFECT

Every successful decision returned:

    "tag_mirror_warning": "Could not find the 'updated_at' column of
                           'judge_tag_assignments' in the schema cache"

`judge_tag_assignments` has no `updated_at` column. Verified on **both** lanes — the column list
is identical in production and staging:

    id, entry_id, tag_id, judge_id, created_at, photo_index, round_number

`submit-judge-decision` upserts `updated_at` into that table, so PostgREST rejects **every**
decision→tag mirror write. The mirror is deliberately non-fatal, so the failure surfaced only as
a warning field on an otherwise successful response. Confirmed by outcome:
**`judge_tag_assignments` = 0 rows after 12 successful decisions.**

This has been failing in production since the code shipped. It was invisible because nobody had
ever run the flow and read the response body. **Fixed in the repo** (the `updated_at` line
removed, with the measurement recorded in place). Not deployed to staging yet — see §7.

Deployed `get-payment-gateways-public` v4 (a real endpoint, not a probe) carrying the new

| `http://www.50mmretina.com` (scheme downgrade) | **ABSENT** |
| `https://attacker.example` | **ABSENT** |
| *(no Origin header — not a CORS request)* | `*` |

Every one of those four refused origins previously received `*`.

**A production-breaking trap was found and avoided.** The audit's recommendation — "emit no ACAO
for a disallowed origin" — would, applied literally, have broken the live Android app.
`capacitor.config.ts` sets `androidScheme: "https"`, so the Capacitor WebView's Origin is
`https://localhost`, which was **not** in the allow-list and reached these endpoints only through
the `*` fallback. **27 functions** use `getSecureHeaders`, including `dashboard-init`,
`get-wallet-summary`, `submit-deposit` and `get-payment-gateways-public` — all called by the app.
The Capacitor origins were therefore added explicitly *before* the fallback was tightened. The
production R2 bucket CORS policy carries the same `https://localhost` entry, for the same reason.

**Production is not weakened:** `https://www.50mmretina.com` is still echoed; the app origins are
now explicitly allowed rather than relying on a wildcard; unknown origins move from a usable
wildcard grant to no grant at all.

## 5. TURNSTILE — MEASURED, AND OWNER ACTION REQUIRED

Discriminator run today (one failed password grant per lane, synthetic address, no `captchaToken`,
nothing mutated):

    production : {"error_code":"captcha_failed",
                  "msg":"captcha protection: request disallowed (no captcha_token found)"}
    staging    : {"error_code":"invalid_credentials",
                  "msg":"Invalid login credentials"}

Production rejects on captcha **before** checking credentials. Staging never checks captcha.
The divergence is measured, not inferred from the code comment.

**Should staging enforce it? Yes.** Otherwise the auth path staging exercises is not the auth path
production runs, and a captcha regression would pass staging and fail production.

**Can the existing production site key cover staging?** Only if `staging.50mmretina.com` is added
to that widget's **Hostname management** list — Cloudflare Turnstile widgets are scoped to a
declared hostname list. The site key `0x4AAAAAAD2cIy9cziOBz3e9` is hardcoded in
`src/lib/turnstile.ts` for all lanes, so whatever widget is used must cover both hostnames.
Whether it currently does is **not readable from any session**.

**OWNER ACTION REQUIRED — one of two configurations:**

* **Option A (recommended for a test lane).** Create a second Turnstile widget using Cloudflare's
  **testing sitekeys** (`developers.cloudflare.com/turnstile/troubleshooting/testing/`), which
  always pass without a real challenge, and set its secret on the staging Supabase project. The
  captcha code path is then exercised on staging — widget renders, token minted, GoTrue validates —
  while scripted testing across the 513 synthetic accounts remains possible. Requires making the
  site key lane-aware in `src/lib/turnstile.ts`.
* **Option B.** Add `staging.50mmretina.com` to the existing production widget's Hostname
  management list and set the **same** secret key on the staging Supabase project
  (Authentication → Settings → Enable Captcha protection → Turnstile). Highest fidelity to
  production; but every automated login on staging then needs a real token, which ends
  script-driven testing.

Production protection was **not** disabled, weakened or worked around.

no longer emits it. The rule named a cross-origin absolute URL as a 200-proxy target, which

the reason travelling with the artifact. Rebuild + guard after the change:
`ISOLATION-GUARD PASS … 385 assets scanned across 3 root(s)` — R2 was not depending on that file.

**`lane-config.mjs` production fallback — DELIBERATELY NOT REMOVED, and the hazard proved closed.**

Making `VITE_SITE_ORIGIN` / `VITE_CDN_HOST` required would break **both** Cloudflare Pages builds:
the CI lanes set them explicitly (`web-build.yml` lines 76, 83, 163, 164) but the Pages projects
do **not** — their variable sets are `ISOLATION_*`, `NODE_VERSION`, `VITE_SUPABASE_*` and G5b's
three Function variables. A required-value change would arm a build failure that fires at G10
promotion. So the hazard was tested instead of assumed:
