## 0.1 · What this pack is, and what it is not

**It is a harness, not evidence.** The compiler has **no access** to either database, the deployed
edge functions, Cloudflare, or GitHub repo settings. **Every result cell in workstreams 1 and 4, and
the execution half of workstream 3, is EMPTY and can only be filled by the auditor under D-13.**

**What the compiler could produce, and did:** the complete 138-file scope manifest (`02a`), derived
from a read-only diff and **self-checked** — 138 rows, 31 added, +9,060 / −1,293, reconciling to the
independently measured totals.

**Do not treat an empty cell as a pass.** An unfilled row is `BLOCKED`, never `N/A`.

## 0.2 · Recording format — mandatory for every check

    Requirement → instrument (exact read-only command/query) → target lane/project/ref
      → UTC timestamp → sanitized output → result → evidence class

**Evidence classes** (§1 of the ledger; no class may be silently upgraded):
`VERIFIED` · `OWNER-ATTESTED` · `INFERRED` · `BLOCKED` · `N/A (with reason)` · `DEFERRED (owner + date)`

## 0.3 · Sanitisation — absolute

- **Never** record credentials, tokens, secrets, connection strings, cookies, session identifiers,
  service-role keys, or unredacted environment values — **not masked, not partial, not hashed.**
  §14 HS-10 treats any of these reaching a log, file, screenshot or chat as a **hard stop requiring
  rotation**. **This has already happened once in this project** (G9 BLOCKER-2).
- **Nobody is ever asked to paste a credential into chat.** Access is granted in each provider's own
  console, to the auditor's own account (D-13, ledger §25.7).
- Redact **before** the value leaves the console. Redact by **removal**, not by masking — a masked
  value is not evidence and can still leak length and prefix.
- Non-secret identifiers that MAY be recorded: project refs, bucket names, token **IDs**, function
  names and versions, policy names, SHAs, endpoints, timestamps.

## 0.4 · Provenance when direct access is unavailable

If a row cannot be checked directly and a **sanitized provider export** is used instead, the export
must carry **all six** of:

| Field | Why |
|---|---|
| **SHA-256** of the export file | integrity |
| **byte size** | integrity |
| **generation timestamp (UTC)** | staleness |
| **source identity** — who generated it, on which account/role | attribution |
| **exact command or query** that produced it | reproducibility |
| **completeness control** (§0.6) | that it is the *whole* answer, not a subset |

**An export without all six is INFERRED, not VERIFIED.**

## 0.5 · Owner-generated vs independently generated — kept apart

| Generated by | Class | Can it close a §25.3 row? |
|---|---|---|
| The **auditor**, under their own read-only access | **VERIFIED** | ✅ yes |
| The **owner**, then handed over | **OWNER-ATTESTED** | ❌ **no** |
| The **compiler** | **VERIFIED (compiler)** — a second source, **never** an audit | ❌ no |

**Owner-generated output stays OWNER-ATTESTED until independently validated. Repetition never
upgrades a class** (ledger §25.4 closure rule). Every row in this pack carries a `GENERATED BY`
field; it is not optional.

**Chain of custody — corrected at revision 3.** The earlier rule said the compiler must never hash
an auditor's export. **That was too broad**: hashing an unchanged file does not make you its author.

**Three distinct roles, recorded separately for every artifact:**

| Role | What they did | Effect on class |
|---|---|---|
| **Generator** | ran the instrument and produced the **original bytes** | **owns the class** — auditor ⇒ VERIFIED, owner ⇒ OWNER-ATTESTED |
| **Custodian** | held or transferred the original bytes **unchanged** | none |
| **Verifier** | recomputed the hash of those **unchanged original bytes** | **none — verification is not authorship.** A second party confirming an integrity hash strengthens the evidence and changes nothing about who generated it |

**The original bytes must be preserved and delivered as-is.** Any **transcription, re-formatting,
re-encoding, spreadsheet round-trip, or excerpt is a DERIVATIVE ARTIFACT** — it gets its own filename,
its own hash, and an explicit label naming **its** author and the original it derives from. **A
derivative never inherits the original's evidence class.**

## 0.6 · Completeness controls — the addition the auditor's brief did not ask for

A SHA-256 proves an export was **not altered**. It does **not** prove it is **complete** — a query
scoped too narrowly returns a clean, authentic, *partial* answer. **That is exactly how C-10
happened**: a search read diff hunks instead of file contents and returned a confident, false result.

**So every export additionally carries a completeness control:** a stated expected count, an
unfiltered total to compare against, or a digest-of-digests. Each check below names its own.

## 0.6a · Identity controls — added after the round-5 review of this pack

**Completeness proves you saw everything the query returned. Identity proves you queried the right
thing.** A perfectly complete, perfectly hashed answer read from the *staging* database is worthless
as a statement about production — and nothing in the first version of this pack would have caught it.

**Every check must therefore capture, in the same output as the result, at least one field that is
unique to the target**: `current_database()` / `current_user` for SQL; the **project ref** for
Supabase; the **account id** and **token id** for Cloudflare; the **repo and ref** for GitHub;
`github.run_id` and `github.ref` for a workflow run.

**Where two lanes are compared, their identity fields must DIFFER.** If they match, one of the two
readings hit the wrong lane and **both** rows are void.

## 0.7 · Negative controls — the second addition

This project has been bitten three times by checks that passed without measuring anything: a UI-gate
sweep that "passed" on a page that never rendered; an isolation gate that silently passed an
unchecked lane (commit `e2db18b6` fixed it); and §8.6's control 3, which **cannot discriminate** for
a correctly-scoped token.

**Every check below therefore carries a negative control that MUST PRODUCE ITS STATED
DISCRIMINATING RESULT.**

> **Wording corrected at revision 3.** The earlier phrasing — *"the negative control must fail"* —
> conflated two different things. A control that correctly returns **zero rows**, an **empty list**,
> or **ABSENT** has *succeeded*: it discriminated. Its process **exits 0**. Meanwhile a control that
> errors out, times out, or 404s on the wrong thing has **not** discriminated at all.
>
> | | Meaning |
> |---|---|
> | **Discriminating result** | the control returned the stated empty/negative answer — ✅ the instrument filters |
> | **Non-discriminating result** | the control returned data it should not have — 🔴 the positive result is void |
> | **Process failure** (unexpected auth / network / parser / command error, timeout) | ⚠ **neither** — the control did not run; record `BLOCKED` |
>
> **Reconciled at revision 4 — an expected error IS a discriminating result.** Several WS1 controls
> are deliberately built on an expected `404`/`No such X` (reading an absent function, an absent
> bucket, an absent environment). Those exit **non-zero by design**, and that non-zero exit is the
> answer:
>
> | Observed | Verdict |
> |---|---|
> | The **specific expected** error, from an **authenticated, target-bound** call (a 404 for the absent object) | ✅ **discriminating** — record the exact status/message |
> | Success where the control expected an error (the absent thing was "found") | 🔴 **non-discriminating** — the positive result is void |
> | Any **other** failure — 401/403, DNS, timeout, parser crash, command-not-found | ⚠ **BLOCKED** — the control never ran |
>
> **So record three things for every control: the exact output, the exit status, and which of the
> three rows above it is.** "It failed" remains meaningless on its own.
>
> **Record the control's actual output and its exit status separately.** "It failed" is not a result.

**If the control does not produce its stated discriminating result, the positive result carries no
information — record the check as `BLOCKED`, not as a pass.**

**One shape: specified, never executed. None of it would have failed loudly on the page.**

**Rule.** Every procedure in this pack carries an execution-provenance tag:

| Tag | Meaning |
|---|---|
| `SPECIFIED, NOT EXECUTED` | written by the compiler; **never run by anyone**. A draft to be confirmed |
| `STATIC-VALIDATED` | **parsed or linted only.** The artifact is syntactically well-formed and its structure was inspected. **It has NOT been executed** and this says nothing about whether it works |
| `FIXTURE-TESTED` | the logic has been **executed by the compiler against synthetic known-answer fixtures**, and passed. Real inputs and real credentials are still untried |
| `SMOKE-TESTED` | the smallest **end-to-end** case has been run by the executing party against the **real** system |
| `EXECUTED` | run in full against the real system, output recorded |

**Current tags in this pack:**

| Artifact | Tag | Evidence |
|---|---|---|
| `07_ws4_reference_impl.py` — lexer, closure, manifest, classifier | **FIXTURE-TESTED** | `08_selftest.sh` **26/26** + `09_rc_regression.sh` **8/8**, run by the compiler. Transcript: `TEST_TRANSCRIPT.txt` |
| Probe workflow YAML (`05_…` §A.3) | **STATIC-VALIDATED** | `yaml-static-validation.txt` — PyYAML 6.0.3 / Python 3.11.15, parsed OK, byte contract stated and cross-checked by two independent extractors |
| **The WS4 provider procedure** (`supabase` CLI steps) | **SPECIFIED, NOT EXECUTED** | ⚠ **must NOT be labelled SMOKE-TESTED until a human auditor completes the provider-backed one-function run** (§4.8) |
| WS1 queries · WS3 commands · the probe run itself | **SPECIFIED, NOT EXECUTED** | — |

**Supported execution platform for the shipped scripts:** POSIX shell (Linux/macOS), **bash ≥ 4**,
**python3 ≥ 3.8**. **LF line endings are required** — both scripts refuse to run and exit 2 on a CRLF
checkout, because CRLF silently breaks heredocs and string comparisons. Each run prints `uname`, bash
version, python version, the implementation's SHA-256, the command, timestamps and the full PASS/FAIL
list. Verified on: `Linux 6.18.44 x86_64`, bash `5.2.21(1)`, python `3.11.15`.

> ⚠ **`STATIC-VALIDATED` is not `SMOKE-TESTED`.** A YAML file can parse perfectly and still be
> untriggerable — **revision 1's probe parsed fine and could never have run.** Parsing proves syntax,
> nothing else. Do not upgrade the tag without a real run.

**Where a command depends on a tool's flags** (`-o json`, `--use-api`, `--project-ref`, `gh api`
paths), the compiler **could not verify them against a live tool**. The executing party confirms them
from `--help` at their pinned version **first**, and records any substitution.
