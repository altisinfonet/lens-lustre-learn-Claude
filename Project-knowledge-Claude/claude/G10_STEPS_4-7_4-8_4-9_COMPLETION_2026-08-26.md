# STEP 4.8(b) — G1 SECOND HALF · ✅ **ANSWERED — no reconfiguration required**

**Runbook:** *"Explain or reconfigure the production Pages project still creating skipped previews for
staging, certificates-to-production and tool/*."*

## The explanation, read directly from the configuration

The Pages settings pane is scoped per environment. Under **Choose Environment → Preview**:

> **Branch control → Preview branch: `None`**

(Production environment, for contrast: Production branch `main`, Automatic deployments **Enabled**.)

**`Preview branch: None` disables automatic preview deployments entirely.** So when any non-production
branch is pushed — `staging`, `certificates-to-production`, `tool/*`, `scratch/*`, `claude/*` — Pages
registers a **deployment record** for the push but **runs no build**. That is precisely why the
deployments list shows those rows with **"No deployment available"** and no URL.

## This is correct behaviour, not a defect

The records are bookkeeping; **no staging-lane code is ever built or served by the production Pages
project.** That is lane isolation working exactly as intended, and it is a positive G1/G8 property
rather than a problem to fix.

**Reconfiguration would be wrong here.** Changing it is a **surface-2** change, which the step 0.0
inventory marks NOT-EXPECTED-TO-CHANGE, and it would *weaken* isolation. The runbook offers "explain
**or** reconfigure"; explanation is the correct branch. **G1(b) closed.**

Corroborating detail: the Preview environment carries **4** variables against Production's **10** —
consistent with a preview lane that never builds.

*(G1(a) — the Zero Trust Access policy — remains **NOT APPLICABLE**: Cloudflare One is not provisioned
on this account. Both halves of G1 are now answered.)*

## N7 — cross-lane key/JWT refusal · ✅ VERIFIED

| # | key → lane | status | reading |
|---|---|---|---|
| A2 | production → **PRODUCTION** `/rest/v1/posts` | **200** | positive control ✅ |
| B2 | production → **STAGING** | **401** | **REFUSED** ✅ |
| C2 | staging → **STAGING** | **200** | positive control ✅ |
| D2 | staging → **PRODUCTION** | **401** | **REFUSED** ✅ |

Literal refusal body (B2, D2):
```
{"message":"Invalid API key","hint":"Double check your Supabase `anon` or `service_role` API key."}
```

Supporting evidence: each key's JWT `ref` claim binds it to its own project (`jtdtehuqtinjxropkkcn` /
`ztzutckwdhetphwghuzj`), so these were true cross-lane attempts; A2 and C2 returned **different row
IDs**, proving separate databases behind separate hostnames; both keys are live and non-expired, so
the refusals cannot be explained by a dead credential. Requests were issued from a neutral
third-party origin so no ambient session could influence the result.

**No key value or fragment appears in any record.**

### 🔴 A trap found, and it would have produced a false green

The prescribed `/rest/v1/` **API root returns 401 for all four cells — including both positive
controls** — because that endpoint requires `service_role`. **A status-code-only assertion there
passes vacuously whether isolation holds or not.** Only the response *body* discriminates:

- `"Only the service_role API key can be used for this endpoint."` → key **recognised** by this lane
- `"Double check your Supabase anon or service_role API key."` → key **not recognised** — the refusal

The test was therefore re-run on a real data path (`/rest/v1/posts`), where the controls genuinely
return 200.

> **Runbook amendment:** if N7 is ever automated, it **must assert on the response body, not the
> status code.**
