## 1. THE DECISIVE MEASUREMENT

Both lanes of the question turned on one thing: **which content-hashed build
artifacts does `www` actually hold?** Vite names every chunk by a hash of its
content, so an artifact either matches a build byte-for-byte or it does not.

A build of `main` HEAD (`32930e7`) was produced locally with the production
job's own public values, on node `22.22.2` — the version `.node-version` pins.
Each resulting artifact was then requested from `www` by its exact hashed name.

| Artifact from the local `main` HEAD build | Contains env values? | `www` response |
|---|---|---|
| `assets/vendor-react-DiS8_lVS.js` | no | **200 — JavaScript** |
| `assets/vendor-query-oRGQe2RW.js` | no | **200** (imported by the above, first line) |
| `assets/index-BLWQIo4R.css` | no | **200 — CSS** |
| `assets/index-DrppXY7Q.js` | **yes** | **404** |
| `assets/AdminSEO-B-yOszlV.js` | **yes** | **404** |
| `assets/vendor-react-ZZZZZZZZ.js` — **known-absent control** | — | **404** |

The control is what makes the 200s evidence. A fabricated hash 404s, so the
host is not answering 200 for arbitrary `/assets/*` paths, and the successful
fetches are genuine content matches. `vendor-react-DiS8_lVS.js` opens with
`import{r as Pe,g as Re,a as u,R as Se}from"./vendor-query-oRGQe2RW.js";` —
naming the second vendor hash from the same local build.

**Two separate non-discriminating instruments were identified and discarded**
before they could mislead:

- `/sitemap.xml` `_redirects` rewrite — G1 already proved Pages rejects that
  rule (`Parsed 0 valid redirect rules`), so both hypotheses predict the static
  file. No information.
- `/_headers` returning the SPA shell — proven to be an extension-based SPA
  rewrite, not Pages consuming the file: `/llms.txt` (extension) returns real
  text while `/_headers` (extensionless) returns HTML. No information.

## 2. WHAT THE PATTERN MEANS

**Env-free artifacts match exactly. Env-bearing artifacts do not.**

On `main`, only three environment variables reach the bundle — verified by
source search: `VITE_SUPABASE_URL` (14 hits), `VITE_SUPABASE_PUBLISHABLE_KEY`
(8), `VITE_SUPABASE_PROJECT_ID` (1). `VITE_CDN_HOST` and `VITE_SITE_ORIGIN`
have **zero** hits on `main` — they are G4 work and exist only on `staging`.

The CSS bundle matching matters independently: Tailwind output is generated by
scanning the source tree, so an identical CSS hash means an identical set of
utility classes across all of `src/`. Together with four identical vendor
chunks, that places `www`'s build on this repository's dependency tree, bundler
configuration, and a source state at or extremely close to `main` HEAD.

**Two named hypotheses for the env difference were tested and both refuted:**

| Hypothesis | Predicted entry chunk | `www` |
|---|---|---|
| H1 — built with the legacy `anon` JWT the CI workflow declares | `index-DrppXY7Q.js` | **404 — refuted** |
| H2 — built with the project's new-style publishable key (id `b6e31e7d…`) | `index-BRwrdrEg.js` | **404 — refuted** |

Both keys are real and currently enabled on the production project; the CI
literal is byte-identical to the legacy `anon` key. Neither produces `www`'s
build.

**Further enumeration would be guessing, so it stops here.** The remaining
explanations — a different Supabase URL, a third key value, a slightly
different source commit, or a combination — cannot be separated without reading
`www`'s entry chunk, whose hash cannot be obtained: it is content-addressed, the
HTML instrument strips `<script>` tags, and unknown `/assets/*` paths 404.

**There is no third Supabase project.** The organisation holds exactly two:
`jtdtehuqtinjxropkkcn` (production) and `ztzutckwdhetphwghuzj` (staging).

## 3. OTHER PUBLIC EVIDENCE GATHERED

**DNS, beyond the A records.** The apex and `cdn` both carry Cloudflare
**HTTPS/SVCB** records with Cloudflare `ipv4hint`/`ipv6hint` and a Cloudflare
ECH config. **`www` carries no HTTPS record at all.** Cloudflare generates these
for proxied hostnames, so their absence on `www` is a third independent
confirmation that `www` is not proxied — alongside the grey-cloud A record and
the documented proxy requirement.

**Zone TXT records** name Brevo (two verification codes plus a DMARC `rua`),
Google site verification, and an SPF include for `spf.stackmail.com`; MX points
to `mx.stackmail.com`. **No Lovable, Vercel, Netlify or other platform
verification token exists anywhere in the zone.** No CAA records are published.

**Certificate Transparency: UNVERIFIABLE-BY-DESIGN here.** Both public CT
endpoints attempted — `crt.sh` and `api.certspotter.com` — are refused by this
session's fetcher under `robots.txt` rules. No TLS certificate or SAN evidence
was obtained, and none is claimed.

**Served static content.** `/robots.txt`, `/llms.txt` and `/sw-image-cache.js`
are served and match this repository's `public/` content, including the service
worker's `gallery-images-v3` cache name — bumped 2026-08-05 and identical on
`main` and `staging`. This dates `www`'s build no earlier than 2026-08-05 and
adds nothing finer.

**Backend identifiers exposed publicly by `www`:** the service worker names
Supabase Storage paths (`/storage/v1/object/public`, `/render/image/public`)
and Cloudflare R2 `*.r2.dev` hosts generically, plus four bucket names —
`portfolio-images`, `competition-photos`, `post-images`, `site-assets`. **It
names no project reference, no account ID and no custom CDN hostname.** No
Supabase ref, R2 account, or Cloudflare endpoint identifier was recoverable
from any publicly served artifact.

**Repository correspondence.** The `.lovable/` directory's test reports are
dated 2026-05-02 and link to `github.com/altisinfonet/lens-lustre-learn` — a
different repository name from the controlled `lens-lustre-learn-Claude` — with
runner paths to match. That repository now returns 404. GitHub redirects
renamed repositories rather than 404ing them, so a simple rename does not
explain it. **This remains leads only.** The artifact evidence in §1 shows
`www` serving builds of the *current* repository's dependency tree and source;
it does not establish which repository the build pipeline reads from.

## 7. ERRATUM E-1 TO MASTER EXECUTION PLAN REV 3.0

**Formally numbered erratum. Rev 3.0 is otherwise unchanged and remains
authoritative. No Rev 3.1 exists.**

> **E-1 — §6 Release Architecture is incomplete.**
> §6 models production as a single Cloudflare Pages lane serving both
> `50mmretina.com` and `www.50mmretina.com`. Measured on 2026-08-22, production
> has **two serving paths**:
>
> * **Path A — the apex**, Cloudflare-proxied, consistent with the controlled
>   Pages lane.
> * **Path B — `www`**, DNS-only to a non-Cloudflare address, serving builds of
>   this repository made with environment values that neither documented
>   production Supabase key reproduces. Outside the isolation guard, `_headers`,
>   Access and the WAF.
>
> The shipped `index.html` redirects Path A to Path B.
>
> **Consequences:**
> 1. **§8.4 (G6)** — a production Pages deploy log line evidences the guard for
>    Path A only. G6's eventual GREEN must be worded to that scope. G6 stays AMBER.
> 2. **§8.5 (G7)** — a staging Pages project mirrors Path A only. G7 may not be
>    designed until the owner rules on Path B.
> 3. **§12 (G10)** — promotion to `main` reaches Path B by an unobserved
>    mechanism. The promotion record must state which paths a release reaches.
> 4. **§16** — Path B is a production surface with no row. Until classified, any
>    change to it is unauthorized by §16's own rule.
> 5. **§14** — no hard stop is declared. Nothing was mutated, and no current
>    gate claim depends on Path B. Should Path B be found to hold production
>    credentials outside every control, that is an **HS-1 assessment**, to be
>    made on evidence rather than on this document's inference.
