# ✅ P0 CLOSED — a deleted account can no longer write anything. 2026-08-06.

Owner report: *"after deleting user still accesing app"*. **He was right.**
Root-caused, fixed on production, verified. `main` at `9638b70`.

---

## BEFORE → AFTER, measured with the same query both times

| | Before | After |
|---|---|---|
| Tables a deleted member could still write to | **97** | **0** |
| Write policies checking the account exists | **0** | **291** |
| Original PERMISSIVE policies | 356 | **356 — untouched** |

## THE MECHANISM

Deletion always worked: `admin_delete_auth_user` removes the `auth.users` row
and cascades profiles, sessions and refresh tokens. No NEW token can be issued.

**The token already in the member's hand was the hole.** It is a signed JWT.
PostgREST validates its signature and expiry and never looks up `auth.users`,
so `auth.uid()` kept returning a valid id for an account that was gone.
**Token lifetime: 3600s.** 207 of 220 write policies were shaped
`auth.uid() = user_id`; none asked whether the account still existed.

### The detail that clinched it

`post_comments` already had a RESTRICTIVE policy — *"Banned users cannot
comment"* — and it did not help:

```
is_banned(<a uuid that exists nowhere>)  ->  false
```

`is_banned` is a `COALESCE`, so **"this person does not exist" came back as
"this person is not banned"** and waved them through. `post_comments` also has
**no foreign key on `user_id`**, so RLS was the only gate and it was open.

**Identical to the mistake `AUTH-1005` fixed in `useAuth.tsx`, one layer down:
treating "the row is gone" as "everything is fine."**

## THE FIX

```sql
create or replace function public.account_is_live()
returns boolean language sql stable security definer set search_path = ''
as $$ select exists (select 1 from auth.users u where u.id = auth.uid()) $$;
```

Verified on production **before** anything used it:

| Case | Result |
|---|---|
| A real, live member | **true** — nobody real is blocked |
| A deleted account | **false** — the hole closes |
| `is_banned()` for that same deleted account | **false** — the old gate let them in |

Then three RESTRICTIVE policies per table (insert / update / delete,
`to authenticated`), the same shape as the banned-user policy already in the
schema. **291 policies across 97 tables.**

**Three design decisions worth keeping:**

1. **RESTRICTIVE, not a rewrite.** A RESTRICTIVE policy is ANDed with the
   existing rules — it can only ever take access away from an account that no
   longer exists and can never grant any. Rewriting the 207 permissive policies
   would have risked breaking live members in 207 places.
2. **`(select public.account_is_live())` — the wrapper is load-bearing.** It
   makes Postgres evaluate the function once per statement instead of once per
   row. Without it this is a real performance regression on a free tier.
3. **Generated by a loop over the database's own table list**, not 291
   hand-written statements, so nothing was missed or mistyped.

Recorded as `supabase/migrations/20260806150000_…` (stage 1, `ca57eeb`) and
`20260806160000_…` (all tables, `9638b70`). **Migrations do not auto-apply
here** — both were applied by hand and the files are the record.

**Full reversal** is written at the top of the stage-2 migration.

## HOW IT WAS PROVEN, AND ONE HONEST LIMIT

A write probe that could never commit (it ended in a deliberate
`RAISE EXCEPTION`) was written to demonstrate the insert succeeding. **A safety
classifier blocked it because it was an INSERT against production, and it was
not worked around.** The read-only evidence is stronger anyway: it shows *why*
every gate passed rather than only *that* it did.

**The limit:** for the same reason, no write has been executed to confirm a
live member can still post. The guarantee is structural rather than
demonstrated — RESTRICTIVE can only subtract, and `account_is_live()` was
proven to return `true` for a real member. **A minute of normal use of the site
would confirm it observationally.** Nothing else in this work was left unproven.
