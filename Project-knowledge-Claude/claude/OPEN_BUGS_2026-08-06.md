## 🔴 THE ONLY UNFIXED BUG — #3, "everything feels delayed"

> Owner: *"like comments anything coming delay, instantly nothing happening,
> delay is there"*

### Located precisely. `src/App.tsx:180`

```ts
const queryClient = new QueryClient({
  defaultOptions: {
    queries: {
      staleTime: 5 * 60 * 1000,      // ← data "fresh" for 5 minutes
      gcTime: 10 * 60 * 1000,
      refetchOnWindowFocus: false,   // ← returning to the app refetches NOTHING
      retry: 1,
    },
  },
});
```

### What was ruled OUT, with evidence
**Likes and comments are not slow.** Both already have optimistic paths —
`src/hooks/feed/usePostReactionMutations.ts` has `onMutate` (lines 107, 139) with
`onError` rollback (116, 148), and comments have their own in `useAddComment.ts`.
The write feels instant because it is applied locally before the server answers.

### What is actually happening
It is the **read** that never happens again. With `refetchOnWindowFocus: false`,
coming back to the app or switching tabs refreshes nothing. With `staleTime` at
five minutes, navigating back to a screen serves whatever was cached. So an
action taken on one device is invisible on another until something forces a
refetch. That reads exactly as *"instantly nothing happening"*.

### The fix, and why it was NOT shipped
`refetchOnWindowFocus: true`, and consider a shorter `staleTime` on feed queries
specifically rather than globally.

**Not shipped** because it changes fetch behaviour for **every member on every
screen** against a free-tier database, and the session that found it had no
capacity left to watch the result or revert. That is the only reason. It is a
small change.

**How to do it safely:** make the change, deploy, then watch Admin → Error Log
and the feed for a few minutes. If request volume looks wrong, revert — it is
one line. Do it EARLY in a session, never at the end.

## ❓ STILL UNKNOWN — #4b, why the file read failed

Bug 4 is fixed (the pipeline now reads a photo once instead of five times), but
the **underlying reason the Android handle refused a second read is not proven.**

**What is proven:** 26 failures, 100% from the app, 0 from web, two real members.
The file WAS read successfully at selection — the preview thumbnail cannot render
otherwise — and then refused at Post.

**The leading hypothesis, explicitly labelled as a hypothesis by the owner
himself:** a picked-file reference goes stale between choosing the photo and
pressing Post. The read-once refactor removes the whole class of problem whether
or not that is right.

**What closes it:** one more failure on build 1054. `FILE-5007` now captures the
DOMException name — `NotReadableError`, `NotFoundError`, `SecurityError` or
`EncodingError`. **Check Admin → Error Log, filter `FILE-5007`.** That name is
the answer.

**One question only the owner can answer, worth asking:** was the photo picked
from the phone's gallery or from a cloud picker (Google Photos / Drive)? A cloud
pick returns a reference that must be re-fetched, which fits a read failing
*after* the preview already worked.

## ⚠️ THE PROCESS LESSON THAT COST THE MOST TODAY

**The app bundles its own copy of the site (`webDir: 'dist'`, no `server.url`).**
Web fixes are invisible on the owner's phone until a build is cut AND installed.

Several fixes were shipped to web for bugs the owner had reported **from the
app**. He tested on the app, saw no change, and called them fake. He was right to.

**Rule for every future session:** if a bug was reported from the app, saying
"fixed" without a build is not a completed task. State it as a blocking
condition in the same message, and push to cut the build — do not leave it as a
closing footnote.
