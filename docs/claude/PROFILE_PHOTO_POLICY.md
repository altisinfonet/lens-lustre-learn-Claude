# The profile photo — the current rule, and the gate that was removed

> ⚠ **READ THIS FIRST.** This document was originally written on 2026-08-01 to
> describe a **mandatory profile-photo gate**. That gate was **removed on
> 2026-08-05 by the owner's order** and must not be rebuilt. The current rule is
> §1. The history is kept below because it explains what `isOwnProfilePhoto()`
> means and why the rule will be rebuilt from it at ~1000 members.
>
> Last updated **2026-08-05**.

---

## 1. THE CURRENT RULE — everyone has a picture, and nobody is blocked

Owner's order, restated three times and then marked final:

> *"I told DP is must, either by user, or by icon generated by 50mm, during
> registration time automatically must be and easy registration will go on.
> after that allow text and photo and comment as normal."*

> **Revised Order / FINAL NOTICE:** *"For DP dont block any users to post
> anything. But DP will be filled up as policy either uploaded by user or filled
> up by system based on the gender. BUt Final Notice : DONT BLOCK ANY USERS for
> DP to post - allow all"*

> *"DP issues resolved. remove every block gate..."*
> *"Even is DP not uplaoded too still users can post antyhing like with DP
> users. simple"*

### Why he stepped back — measured, not argued

Posts per day: **20, 15, 19** (Jul 29–31) → **10, 9, 12, 7** (Aug 1–4). The gate
went up on 2026-08-01. **32 of 83 active members (39%)** had no *uploaded* photo
and could not post **or** comment at all; four of them had been posting before
the rule landed and were never told why it stopped.

### How it works now

**a. The database hands out a picture at registration.**
`supabase/migrations/20260805120000_fallback_avatar_at_registration.sql`.
`handle_new_user()` assigns one of our own ten cartoons in the same INSERT that
creates the profile — there is no window in which a member exists without a
picture, and no client has to remember to do it. Web, app, Google sign-in and
any future path all go through this one trigger.

Gender is not known at that moment, so per the owner's formula — *"by default
male image will fill up but when user select she instaly female any icnon will
take place"* — the **male five** are the default, and
`trg_sync_fallback_avatar_to_gender` re-points it the instant the member answers
He / She, **keeping the slot** (f3 → m3, never f3 → m1). An uploaded portrait is
never re-pointed, and neither is a member who deliberately picked a different
cartoon afterwards.

**b. No write may ever blank it.** `trg_ensure_member_always_has_picture`
(BEFORE INSERT OR UPDATE OF `avatar_url`) turns any write that would leave
`avatar_url` NULL or empty into an assignment of the fitting stand-in.

This was added after a bug of mine: removing the photo requirement from
onboarding made `handleFinish` write `avatar_url: ""` for anybody who skipped
it, which **overwrote the assigned cartoon**. It hit one member — the owner's
own test account — before it was caught. The client bug is fixed, but *"DP is
must, either by user, or by icon generated by 50mm"* is a rule about the DATA,
so the database is where it belongs. No client, present or future, can undo it.

**c. Nothing blocks.** The three RESTRICTIVE policies are dropped
(`20260805060000_remove_profile_photo_gate.sql`), and `Layout.tsx` no longer
opens the onboarding modal for a missing photo — only for a missing **username**
or **member type**, which are structural (the username is part of the member's
public URL and is permanent).

**d. The "add a photo first" *message* is gone too.**
`PROFILE_PHOTO_REQUIRED_MESSAGE` and `isMissingPhotoError()` were deleted from
`src/lib/profilePhoto.ts`. They guessed "you have no profile photo" from a bare
Postgres 42501, which is all a RESTRICTIVE policy failure reports. With the photo
policies gone, the RESTRICTIVE policies that remain are the **"Banned users
cannot …"** ones — so that guess would now tell a banned member to upload a
photo, putting the removed wall back in front of somebody it never applied to.
The real error message is shown as-is.

### Verified on production, 2026-08-05

| Check | Result |
|---|---|
| Policies anywhere referencing `has_profile_photo` or `avatar_url` | **0** |
| RESTRICTIVE policies left on `posts` / `post_comments` / `post_reactions` / `comments` | only `Banned users cannot …` |
| Members with no picture | **0** of 84 (33 on a system cartoon) |
| Member with only a cartoon: text-only post, comment, reaction | **all three INSERTs succeeded** under their own JWT with RLS active, in a rolled-back transaction |

### What is deliberately KEPT

- **`isOwnProfilePhoto()`** — a *definition*, not a gate: the single statement of
  "a photo the member actually uploaded". Used to decide whether to offer a
  stand-in cartoon, and it is what the rule is rebuilt from at ~1000 members.
- **`public.has_profile_photo()`** — kept, referenced by nothing, same reason.
- A cartoon **still does not count as a profile photo**. The value is a
  site-relative path; both allowlists cover our own upload storage only. So the
  optional "add your photo" invitation still makes sense.

### The line not to cross

> *"I step back from my policy but I will again push it once I have 1000
> members, I will wait till then."*

Until he says so: **do not add any check, policy, trigger, modal or toast that
prevents a member without an uploaded photo from posting, commenting or
reacting.** Two describes pin this in
`src/lib/__tests__/profilePhoto.test.ts` — *"nothing may refuse a post or comment
for a missing photo"* and *"the gate that was dropped stays dropped"*.

## 2. HISTORY — why `isOwnProfilePhoto()` exists (2026-08-01)

Written after the owner asked why members were still enrolling without a profile
photo weeks after the "strict DP policy" shipped.

Measured across 77 live profiles:

| What the profile photo actually was | Count |
|---|---|
| A real photo uploaded to `cdn.50mmretina.com` | 36 |
| **A Google account picture (`lh3.googleusercontent.com`)** | **31** |
| Nothing at all | 8 |
| Old Supabase storage bucket (genuine uploads) | 2 |

Nobody had completed onboarding with an empty `avatar_url`. The policy was not
being skipped — it was being **satisfied by a picture the member never chose.**

**Hole 1 — a Google picture counted as a profile photo.** Supabase's Google
sign-in wrote the member's Google account picture into `profiles.avatar_url` at
account creation. The gate asked `!profile.avatar_url`, which was already false,
so for 31 of 77 accounts it never opened. `OnboardingModal` pre-filled from the
same value, so its "Continue" was already unlocked.

**Hole 2 — the account exists before the gate runs.** The `profiles` row is
written the instant someone signs up; the requirement was a React modal on the
*next* render. Close the tab and the account persists with no photo. That is
the 8.

**Hole 3 — nothing enforced it below the UI.** No `NOT NULL`, no `CHECK`, no RLS
policy, no trigger touching `avatar_url` across all 564 migrations. The entire
"strict policy" was one `useEffect`.

**The answer to all three** was one definition, an **allowlist** (not a
denylist — the next OAuth provider or Gravatar is refused by default):

```ts
isOwnProfilePhoto(url)  // true only for https://cdn.50mmretina.com/… or …/storage/v1/object/public/avatars/…
```

mirrored in SQL as `public.has_profile_photo(uuid)`.

The gate built on top of it (three RESTRICTIVE INSERT policies on `posts`,
`post_comments`, `comments`, admins exempt) is the thing that was **removed on
2026-08-05** — see §1. RESTRICTIVE was the right shape for a gate: PERMISSIVE
policies are ORed and can only loosen access; RESTRICTIVE is ANDed with every
other policy. Worth remembering if the rule is rebuilt.

## 3. 2026-08-03 — Google stopped serving the hotlinks

**Measured on the live feed:** every avatar on `cdn.50mmretina.com` returned
200; every `lh3.googleusercontent.com` avatar returned **HTTP 503**. 27 of 81
members still carried such a URL, so their faces were broken circles on every
surface, and a brand-new member's picture broke the moment they joined. Owner
report: *"login time image not loading, joining time image not loading."*

The prediction in Hole 1 ("a hotlink that can stop resolving") came true.

**Fix — `supabase/migrations/20260803210000_no_hotlinked_avatars.sql`:**

1. `handle_new_user()` stopped copying the OAuth picture at signup.
2. `sync_oauth_on_login()` stopped restoring it on later logins. (The sneaky
   one: it re-wrote the hotlink whenever `avatar_url IS NULL`, so a data fix
   alone would have regressed on each member's next sign-in.)
3. Backfill: the 27 hotlinked values → NULL. The 44 CDN photos and 2 legacy
   storage uploads untouched.

Rehearsed in a rolled-back transaction, then applied, then verified three ways.
**Proof after:** a full feed load makes **0** requests to googleusercontent
(was: several, all 503) — 117 resources, 56 images, 0 broken.

No app release was needed: avatar URLs come from the database at runtime.

> Note the interaction with §1: `handle_new_user()` was later changed **again**,
> on 2026-08-05, to assign one of *our own* cartoons. That is not a
> reintroduction of the hotlink — nothing external is copied.

## 4. Rules for whoever touches this next

- **Do not rebuild the gate** without the owner saying so. See §1.
- **`isOwnProfilePhoto()` (TS) and `has_profile_photo()` (SQL) must stay in
  sync.** A test reads the migration and asserts both patterns are still there.
- **Never widen the allowlist to a provider's host.** The original defect was an
  external picture counting as a profile photo.
- **Do not "fix" empty circles by copying Google pictures into our storage.** It
  would make the database look healthy while the member still never chose a
  photo. (Since 2026-08-05 there are no empty circles anyway — see §1.)
- **Never reintroduce the OAuth-avatar copy in `handle_new_user` or
  `sync_oauth_on_login`.** Google 503s the hotlinks and they never satisfied the
  policy anyway.
- **Never make the assigned cartoon count as a profile photo.** It is a
  stand-in; both allowlists cover our own upload storage only.

Gate shipped: web `2026-08-01-16`, Android **1035**.
Gate removed: web `2026-08-05-1`; database changes applied directly to
production, no build required.
