## 0 · Why this file exists

- "M11" appears in three gate sentences (P11 clause 3, P13, P16) and is **defined nowhere** (`git grep M11`, staging `b2aa236`; D2 noted this in `docs/evidence/d2/P11/bare-img-lint.md` and `P13/bundle-budget.md`).
- MASTER R-93 used "M11" for the **bare-`<img>` count ratchet**. That counter already exists and is enforced as P11 **clause 2** (`eslint-rules/no-bare-img.js`, baseline 225 in 110 files).
- The three gate sentences, however, all use M11 as a **byte budget**: "feed bytes … against M11's budget" (P11), "fails, it does not warn, in the same style as M11" (P13), "bytes-per-feed-screen re-measured against M11" (P16).
- **Proposal:** M11 = the byte budget below, and the `<img>` counter is called **"the P11 lint ratchet"**. The Auditor amends R-93's wording; no code changes.

## 1 · Definition

**M11 = the image bytes a member downloads to see the first screen of a post in the feed, on the 3G-class profile.**

| term | exact meaning |
|---|---|
| surface | a feed card at full width. Measured on **`/post/:id`** for public posts (the same `PostMedia` component, `srcSet` and `sizes="(max-width: 768px) 100vw, 600px"` as the feed). The signed-in `/feed` is added as soon as a probe account exists (§4.3) |
| "first screen" | navigation start → every `<img>` that intersects the first 800 CSS px is `complete` (at least one post or portfolio image among them), then 3 s settle |
| bytes | `Network.loadingFinished.encodedDataLength` (bytes on the wire, headers included) for requests of CDP type `Image`, summed. **Service worker blocked and cache disabled**, so it is a cold first view |
| 3G-class profile | `android-mid-2026` = the P17/P0 harness profile: 360×800 CSS px @ DPR 3, mobile, CPU 4× throttle, **150 ms RTT, 209,715 B/s down, 96,000 B/s up** (Lighthouse's mobile "slow 4G / regular 3G" class). This is the profile the gate means by "3G" |
| statistic | the **median over a fixed corpus of 10 public posts** (§4.1), 1 run each |

The budget has three numbers:

| | budget | why |
|---|---|---|
| **M11-screen** · first-screen image bytes, median | **≤ 350,000 B** | one 1080 px-wide WebP feed image at good quality is ~150–250 KB; plus avatar, logo and UI |
| **M11-image** · largest single image on the first screen, worst post | **≤ 250,000 B** | stops a single original-size file from blowing the screen |
| **M11-slow** · first-screen image bytes when OFF-3 classifies the network as `slow` | **≤ 150,000 B** | OFF-3 already switches PostMedia to the smallest rung when slow; this gives that switch a number |

**Against the budget today:**
- **M11-screen:** median 512,707 B against a 350,000 B budget → **FAIL by 46 %**. Only 2 of the 10 posts are under 350 KB.
- **M11-image:** worst post 1,059,877 B against a 250,000 B budget → **FAIL**. Only 3 of the 10 posts have their largest image under 250 KB.
- **M11-slow:** **not measurable on production.** OFF-3's slow rung is on staging only (#362); it is measured on staging once it merges.

**For comparison, the signed-out landing page `/`:** 57,791 B of images (4 images, all from `www`, all UI). It is not the feed, so it is not part of M11.

**Cause, read from the code** (`src/components/post/PostMedia.tsx:264,311–335`, staging `b2aa236`):
- At 360 CSS px × DPR 3 the browser needs a ~1080 w candidate.
- The `srcSet` offers `thumb 600w[, rung 1080w[, rung 1440w]], original 1920w`. When a post has no 1080 w rung, the next candidate is the **1440 w rung or the 1920 w original**.
- That is why single images reach 0.7–1.06 MB.
- **The lever (D2's fix unit, not this file):** add a 720 w rung, and/or cap the effective DPR at 2 in `sizes` for the feed. Either brings a 360 px screen to a ≤ 720 w candidate.

**Instrument notes (for repeatability):**
- The first probe version waited only for `networkidle`. It measured 0 CDN bytes, because the post data arrives about 5–10 s later under this profile.
- With the production image service worker allowed, CDP page-level bytes were also hidden.
- The committed probe therefore (a) blocks service workers and (b) waits until a post image is `complete`. Both are recorded in the file.

## 3 · How "before and after" is judged (P11 clause 3's sentence)

- **Before** = §2 (median 512,707 B / worst image 1,059,877 B).
- **After** = the same corpus, the same probe, after D2's image-ladder unit merges and deploys.
- **P11 clause 3 is closed when the "after" run meets all three budgets**, or when the Owner signs a revised budget. Either way, a remeasurement goes in this folder beside the baseline.

## 4 · Enforcement (D2 builds it; one PR; shown failing first)

1. **Corpus:** `docs/evidence/d2/phase5/P11/m11-corpus.json` holds 10 public post ids.
   - **Selection rule:** the 10 newest `privacy='public'` posts in the production sitemap function at selection time.
   - **Re-selected only when** a corpus post is deleted or made private, and the change is a reviewed PR.
2. **Check:** `scripts/web-m11.mjs` = the §2 probe as a script.
   - It runs **after the deploy serves the pushed commit** (the F-AUD-1 wait) on every main push, and on staging for `slow`.
   - It **FAILS** when any of these holds:
     - M11-screen median > budget;
     - M11-image > budget;
     - M11-slow > budget (staging);
     - the median rises by more than 5 % over the committed last-good value (a ratchet, so a regression fails even while still above budget during the transition).
   - Until the ladder fix lands, the check runs in ratchet-only mode against §2's numbers, and switches to budget mode in the same PR as the fix.
   - Fail-first: temporarily point PostMedia's feed `sizes` at `1920px` → the check goes red → revert.
3. **Signed-in feed:** the Owner creates one **staging probe account** with no real data, and stores its credentials **only as a GitHub Actions secret** (sessions never see them). D1 seeds it a feed of 10 posts copied from the corpus derivatives. `web-m11.mjs --feed` then also measures `/feed`. Until that account exists, `/post/:id` is the measured surface, and this is recorded in every run.
