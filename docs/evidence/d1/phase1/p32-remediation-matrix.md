## 2 · §4.6 — ORDERING AND COLLISION ANALYSIS

### 2.1 · F-62 / F-66 — the rule every statement in this phase is written to

Two separately measured facts, both already recorded in the repository:

1. **`REVOKE … FROM anon` is a no-op wherever `PUBLIC` holds the grant.** All 78 rows carry the
   leading `=X/postgres` ACL entry. Every statement must be `REVOKE ALL … FROM public` **first**,
   then the named grants.
2. **A closed function reopens on `DROP` + `CREATE`.** `CREATE OR REPLACE` preserves the ACL;
   `DROP` + `CREATE` restores Postgres's built-in EXECUTE-to-`PUBLIC` default. Any later migration
   that recreates one of these objects reopens it silently, and the closure must be re-proved after
   it — which is what the `PROBE_` files are for.

### 2.2 · Hard ordering constraint — `get_broadcast_feed`'s three signatures

```
get_broadcast_feed(uuid[], int)            ─┐
                                            ├─►  get_broadcast_feed(uuid[], int, int, text[])   ← the real body
get_broadcast_feed(uuid[], int, int)       ─┘
```

Both wrappers are `SECURITY DEFINER` and call the 4-arg form, so the inner call is made **as the
definer and does not consult the caller's grant**.

**Consequence:** closing the 4-arg alone changes nothing an attacker cares about — the two wrappers
remain an open front door to the same body. **The three must close in one statement, in one
migration, or not at all.** This is the one genuine ordering constraint in the population and it is
invisible at the name level; a name-level count (28) hides it behind a row count (30).

### 2.4 · Prospective group order, and the reason for it

1. **`internal/service-role only` (28 rows).** No client role holds a legitimate call. Zero caller
   risk, largest reduction, and it makes the remaining population small enough to reason about.
   Split by table per §2.3 — do not send 28 revokes in one file.
2. **`grant-only closure` where the caller is session-gated (30 rows).** `REVOKE FROM public, anon`
   + `GRANT TO authenticated, service_role`. This is #274's shape and it is the right one.
3. **`get_broadcast_feed` ×3 as one indivisible unit** (§2.2), after the Owner rules.
4. **`body-level fix required` (6 rows).** These need an expand → behaviour → contract sequence of
   their own, not a grant file. PR #276 already carries four of them.
5. **`no caller — written disposition owed` (8 rows).** *Restore or remove honestly* comes first;
   revoking a dead object and calling it progress is the thing the skill warns against.
6. **`intentional public` and `Owner decision pending` (6 rows).** Last, and only after a ruling.

### 2.5 · Cross-lane collision that is already live

`0024` is **two different files on two lanes** — staging `0024_p32mail_delete_email_revoke.sql`,
main `0024_f105de_referral_reward_production_close.sql`. Any P32 file that assumes a single `0024`
is wrong on one of the two lanes. Recorded in the kickoff §2; repeated here because the matrix's
group 1 and group 2 both land in that range.

### 2.6 · Dispatch state is not closure state

Four objects in this matrix carry a **merged but not applied** revoke — `delete_email`,
`emit_notification`, `move_to_dlq` (PR #258) and `set_write_path` (PR #262). They read
`anon=X/postgres` live, today, 2026-09-22T05:31Z. Nothing in this matrix treats a merged migration
as a closed object, and the `PROBE_` files are written to fail against exactly this state.
