## 3 · The discriminating test — the assertion shown failing against the real defect

R-8 §7 asked for the auth-admin assertion to be built **first** and shown **failing against a

### 3.1 · Merged `0029` on the staging shape — the outage, demonstrated

```
starting ACL : postgres=X | =X/postgres | anon=X | authenticated=X | service_role=X
               PUBLIC entries=1   auth_admin effective=t   auth_admin NAMED=f
```

### 3.3 · ⚠ The fixture caught a defect in *this unit's own file*, and it is recorded

The first harness run failed. Not on `0029` — on `0038`, at the **idempotence** step.

The apply records what it did in a marker so its rollback can tell the lanes apart. On a **second**
run it re-read the live ACL, saw the grant **it had added itself**, concluded the grant
pre-existed, and rewrote the marker to `added=false`. The rollback then took the wrong branch and
left staging holding a named grant it never had.

A real defect, in a real safety mechanism, found because R-8 §7 requires an idempotence step. The
fix makes the **first observation authoritative**: if a marker already exists, its value is kept
and the live ACL is not re-read. Proved:

```
[re-apply] NOTICE: RE-RUN — existing marker says this file added the grant; preserving that.
[re-apply] NOTICE: MARKER WRITTEN — [R8-0038 auth_admin_grant_added=true]
idempotence: ACL byte-identical after re-apply ✅
marker after re-apply: [R8-0038 auth_admin_grant_added=true]   (still true)
```

Recorded rather than quietly patched. A harness that has caught something is the reason to trust
the run that follows it — and this one caught the same *class* of error the unit exists to correct:
reading current state and mistaking it for history.

### 3.4 · Rollback, both shapes — the two-lane problem solved without a file variant

**Why state alone cannot decide it.** The apply is convergent: from the staging shape or the
production shape it produces the identical ACL `postgres | service_role | supabase_auth_admin`.
After the fact, no read of `pg_proc`, `pg_authid` or `current_database()` distinguishes them. Not a
hard question — an unanswerable one. Hence the marker.

| | FIXTURE A — staging shape | FIXTURE B — production shape |
|---|---|---|
| starting ACL | `postgres \| =X/postgres \| anon \| authenticated \| service_role` | `postgres \| service_role \| supabase_auth_admin` |
| PUBLIC / auth-admin NAMED before | held / **absent** | absent / **held** |
| apply | closes PUBLIC, anon, authenticated; **adds** auth-admin | **no-op proved** — ACL byte-identical before and after |
| marker written | `added=true` | `added=false` |
| rollback branch | revokes the added grant | **leaves the pre-existing grant alone** |
| PUBLIC after rollback | **0** | **0** |
| auth-admin NAMED after rollback | **f** — pre-apply state restored | **t** — GoTrue's path intact |
| post-rollback ACL | `postgres \| service_role \| anon \| authenticated` | `postgres \| service_role \| supabase_auth_admin \| anon \| authenticated` |

One file, both lanes, no `_STAGING`/`_PRODUCTION` variant invented (§6.2 reserves that to the
Auditor). **PUBLIC is never recreated on either shape.**

If the marker is ever edited away the rollback fails **safe** — it leaves the grant in place, and
says so with a `WARNING`. Leaving staging marginally more closed is recoverable; revoking
production's only named path to its auth hook is an incident.
