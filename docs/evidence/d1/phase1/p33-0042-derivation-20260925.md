# 0042 — derivation, decisions and findings

Everything below was measured on staging (`fpszggreishhuvdpkmdr`, PostgreSQL
17.6) on 2026-09-25 with `SELECT` only, or read out of the repository at
`c583431`. Behaviour was measured on a scratch PostgreSQL 17.11 cluster;
the transcript is `p33-0042-transcript.txt`.

---

## 1. The defect, restated from the catalogue

Both views carry this, verbatim from `pg_get_viewdef`:

```
WHERE EXISTS ( SELECT 1
         FROM competition_entries ce
           JOIN competition_round_publish crp ON crp.competition_id = ce.competition_id
        WHERE ce.id = <row>.entry_id
          AND ce.user_id = auth.uid()
          AND crp.published_at IS NOT NULL )
```

The entry is correlated. The owner is correlated. The round is not. `crp` is
joined on `competition_id` alone, so the `EXISTS` is satisfied by **any**
published round of that competition. `judge_decisions_owner_safe` carries
`AND crp.round_number = jd.round_number` and is correct.

Measured ACL and shape of both views, identical, the 0033 post-state:

```
relkind v · owner postgres · reloptions NULL (security_invoker unset)
{postgres=arwdDxtm/postgres,anon=r/postgres,authenticated=r/postgres,service_role=arwdDxtm/postgres}
0 PUBLIC ACL entries
```

Column lists (unchanged by 0042, and `CREATE OR REPLACE VIEW` could not change
them):

* `judge_comments_owner_safe` — `id, entry_id, photo_index, comment, created_at`
* `judge_tag_assignments_owner_safe` — `id, entry_id, tag_id, photo_index, round_number, created_at`

Dependents: **none**. No view, function or policy references either one
(`pg_depend` → `pg_rewrite` / `pg_proc`, and `pg_policy`).

## 2. Where the round comes from

### Tags — direct

`judge_tag_assignments.round_number` is `integer NOT NULL`. On staging: 1 row,
0 NULLs. The correlation is `crp.round_number = jta.round_number`.

### Comments — indirect, and this is the part the ruling asked to be derived

`judge_comments` has **no** round_number column. Its foreign keys are:

| constraint | column | references |
|---|---|---|
| `judge_comments_entry_id_fkey` | `entry_id` | `competition_entries(id)` |
| `judge_comments_round_id_fkey` | `round_id` | `judging_rounds(id)` |

`judging_rounds` is:

```
id uuid NOT NULL, competition_id uuid NOT NULL, round_number integer NOT NULL,
name text NOT NULL, description text, status text NOT NULL, created_at timestamptz NOT NULL
```

8 rows on staging, two competitions × rounds 1–4, `round_number` values
`1,2,3,4`. So the mapping is

```
judge_comments.round_id  ->  judging_rounds.id  ->  judging_rounds.round_number
```

and it is the only one: there is no other round-bearing column and no other
foreign key on `judge_comments`. 0042's precondition asserts the foreign key
exists rather than trusting the column name.

## 3. Two fail-closed decisions, flagged rather than assumed

### 3.1 `judge_comments.round_id` is NULLABLE

Measured: `attnotnull = false`. A comment with no round cannot be shown to
belong to a published round, so after 0042 it is **not returned**.

`judge_comments` has **0 rows on staging**, so the size of this is unmeasurable
there, and production is unmeasured (BLOCKER-B). The alternative —
`(jc.round_id IS NULL OR <correlation>)` — reopens C-A19 for exactly those
rows, which is why it was not taken. The static scan asserts that escape hatch
is absent, and the fixture carries a NULL-round comment so the choice is
exercised rather than described.

**If the Owner wants NULL-round comments to remain visible to their owner, that
is a product decision and a one-line change to this file.**

### 3.2 the comment's round must belong to the entry's competition

The new `EXISTS` also requires `jr.competition_id = ce.competition_id`. Without
it the correlation is on a bare integer: a `round_id` pointing at **another**
competition's round 3 would be unlocked the moment the owner's own competition
published **its** round 3. That is a smaller version of the same mistake
C-A19 is.

This is a strengthening beyond the literal wording of the ruling and is called
out for acceptance. The fixture carries a comment on member A's entry in
competition C whose `round_id` points at competition **D**'s round 1 — a
published round of a competition A has no entry in — so the clause is measured,
not asserted.

## 4. FINDING · the application already documents the behaviour 0042 installs

Standing Rule 21: an instructing comment is a control, and a comment that
disagrees with its code is a finding. Three call sites state the guarantee the

|---|---|
| `src/hooks/dashboard/useDashboardData.ts:182` | "publish-gated owner-safe views (no judge_id leak, and **zero rows pre-publication regardless of round**)" |

| `src/hooks/competition/useCompetitionDetail.ts:176` | "publish-gated owner-safe view … **zero rows pre-publication**" |

0042 does not change the intended contract. It makes the database keep the one
the application was written against.

## 5. What each call site sees differently after 0042

App readers of the two views at `c583431` (shape-independent `.from()` scan):

| call site | reads | selects | change after 0042 |
|---|---|---|---|
| `src/pages/SubmissionDetail.tsx:372` | tags | `entry_id, tag_id, photo_index, created_at` | rows from rounds that are not published stop arriving |
| `src/pages/SubmissionDetail.tsx:374` | comments | `entry_id, comment, photo_index` | same |
| `src/hooks/dashboard/useDashboardData.ts:184` | tags | `entry_id, tag_id, photo_index, created_at` | same |
| `src/hooks/dashboard/useDashboardData.ts:186` | comments | `entry_id, comment, photo_index` | same |
| `src/components/EntryTagStamps.tsx:39` | tags | `tag_id, photo_index, created_at`, newest 1 | the "latest" tag can now be an older, published one instead of an unpublished newer one |
| `src/hooks/competition/useCompetitionDetail.ts:181` | tags | `.eq("round_number", 4)` | R4 tags arrive only once **round 4** is published, not once any round is |

Two things are worth the Auditor's attention here:

* `SubmissionDetail` computes `publishedRoundsForFetch` from
  `competition_round_publish` and gates some of its own rendering. The tag
  reads select no `round_number`, and **the comment view exposes no round
  column at all**, so the client cannot gate comments by round even if it
  wanted to. The comment leak is server-side and currently unmitigated.
* `EntryTagStamps` takes `.order("created_at", desc).limit(1)`. Its result can
  change, not merely shrink. That is the intended behaviour — an unpublished
  round's tag should not be the stamp a participant sees — but it is a visible
  UI change and not only a tightening.

**Outstanding — D2:** one-line confirmation that nothing in `SubmissionDetail`,
`EntryTagStamps`, `useCompetitionDetail` or `useDashboardData` depends on
receiving rows from unpublished rounds. D1 has read all four and found no such
dependency; the confirmation is D2's to give, and this PR is a draft until it
does.

## 6. CORRECTION · F-66 does not apply to views

0042's first draft justified `CREATE OR REPLACE VIEW` by citing F-66 —
"DROP+CREATE reopens the default PUBLIC grant". **That is wrong for tables and
views**, and the correction matters because a guard written for the wrong
hazard would not have caught the real one.

Measured on PostgreSQL 17.11 (`p33-0042-run-tests.sh` step 7, which re-runs it
on every execution):

```
BEFORE DROP+CREATE  acl={postgres=arwdDxtm,anon=r,authenticated=r,service_role=arwdDxtm}
                    anon=t  authenticated=t  service_role=t
AFTER  DROP+CREATE  acl=(null)
                    anon=f  authenticated=f  service_role=f  PUBLIC=f
```

`relacl` resets to NULL and the relation gets a new oid. For a view the
built-in default is owner-only, so **PUBLIC gains nothing** and `anon`,
`authenticated` and `service_role` all **lose** SELECT. The six KEPT views'
live call sites and every service-role reader would start failing with 42501,
silently, at the next read.

F-66's PUBLIC-reopening form is a **function** phenomenon: PUBLIC holds EXECUTE
on functions by default. The conclusion for 0042 is unchanged — do not DROP and
CREATE — but the postcondition asserts the **oid** and the **whole ACL string**
rather than only the absence of a PUBLIC entry, because only that catches the
real failure.

**For the Auditor:** other P33 files cite F-66 for views in passing —
`20260910_0036`'s `COMMENT ON VIEW public.judging_progression_audit` ends
"(F-62/F-66 apply)". That is an over-citation in a comment string, not a
control defect; 0036's own guards are ACL assertions and are unaffected. D1 did
not amend 0036 for it because that unit was already handed off for push, and
raises it here instead.
