# 0044 — plpgsql_check out of `public`: derivation, decisions, limits

P33 clause 4. Measured on staging (`fpszggreishhuvdpkmdr`, PostgreSQL 17.6) on
2026-09-25, **SELECT only**; behaviour measured on scratch PostgreSQL 17.11 with
plpgsql_check 2.10 installed from PGDG. Transcript: `p33-0044-transcript.txt`.

## 1. How staging's copy got into `extensions`

**Not by any migration.**

| measured on staging | value |
|---|---|
| `pg_extension` | plpgsql_check **2.8**, schema **extensions**, owner **`supabase_admin`**, `extrelocatable = false` |
| `supabase_migrations.schema_migrations` statements mentioning plpgsql_check | **0** |
| files in this repository creating/altering/dropping it | **0** (the bootstrap only lists it as a prerequisite) |
| `supautils.privileged_extensions` | includes **plpgsql_check** |
| `supautils.privileged_extensions_superuser` | **supabase_admin** |
| `postgres` | `rolsuper = false`, not a member of `supabase_admin` |

An extension owned by the supautils delegate, on the privileged list, with no
migration behind it, is the platform path: a `CREATE EXTENSION` issued as
`postgres` — from the dashboard or from SQL — that supautils runs as
`supabase_admin`, which then owns the result. The schema is chosen at creation;
staging's was created with `extensions`, production's with `public`.

## 2. Relocatable? No — so it is DROP + CREATE

Control file: `relocatable = false`. Staging agrees: `extrelocatable = false`,
and `pg_available_extension_versions` lists 2.7 and 2.8, both non-relocatable,
both `superuser = true, trusted = false`.

Measured, with the extension in `public`:

```
ALTER EXTENSION plpgsql_check SET SCHEMA extensions;
ERROR:  extension "plpgsql_check" does not support SET SCHEMA
```

The one-statement move does not exist.

## 3. Who is allowed to drop and create it — the one thing no fixture proves

plpgsql_check is superuser-only. The dispatch workflow connects as `postgres`,
which on Supabase is neither a superuser nor a member of the owner. The file
works only through supautils delegation, whose README states that privileged
extension creation is delegated to the configured superuser and that
*"this also works for updating and dropping privileged extensions."*

That is **documented** behaviour, **consistent** with staging's measured
ownership, and **not exercised** here — the scratch cluster has no supautils.
The harness shows both halves it can:

* as a non-superuser with no delegation, 0044 refuses at `P33-0044-PRE-004`
  **before touching anything** (digest unchanged);
* as `supabase_admin` — standing in for the delegation's result — the move
  works, round-trips, and ends byte-exact.

If the platform refused the DROP despite the README, the statement fails with
`must be owner of extension plpgsql_check` inside the transaction and nothing
changes. The failure mode is safe; the success path is unverified off-platform.

## 5. Why it matters — measured versus assumed

**Measured (staging):** the 24 member functions carry
`{=X/supabase_admin, supabase_admin=X/supabase_admin, postgres=X*/supabase_admin}`:
EXECUTE for PUBLIC, so for `anon`. None is SECURITY DEFINER. Several are
VOLATILE and act on server-wide state — `plpgsql_profiler_reset_all()`,
`plpgsql_profiler_install_fake_queryid_hook()`, `plpgsql_check_tracer(...)` —
and `plpgsql_check_function(regprocedure, …)` analyses any function by oid.

**Assumed (platform default, not readable from SQL):** Supabase exposes
`public` and `graphql_public` through PostgREST and not `extensions`. In
`public`, every one of those functions is callable at `/rest/v1/rpc/<name>`.

**Modelled (fixture, from staging's `supabase_admin` default privileges):** in
`public` they would carry `{=X, postgres=X, anon=X, authenticated=X,
service_role=X, supabase_admin=X}`. Production's actual ACLs are **not known**;
the probe reads them.

After the move, anon can still EXECUTE them — exactly as on staging. What
changes is **where they live**. 0044 is a location fix, not an ACL fix, and it
says so.

## 6. Instrument defects found in this unit, all fixed

1. **The caller check searched for the wrong string.** PRE-006 first looked
   for `plpgsql_check` in function bodies. The extension's functions include
   `plpgsql_profiler_*`, `plpgsql_coverage_*`, `plpgsql_make_pragma` and
   `__plpgsql_show_dependency_tb`, none of which contains that string, so a
   body calling `public.plpgsql_profiler_reset_all()` passed. Harness step 8b
   caught it. PRE-006 and PRE-007 now match the members' names, captured from
   `pg_depend`, as whole words. The static scan fails a regression to the
   string-only form.
2. **The rollback's postcondition and the harness counted by name pattern**
   (`LIKE 'plpgsql%'`), which misses `__plpgsql_show_dependency_tb`: 23 of 25.
   Both now count by extension membership and by captured member names.
3. **The fixture tripped the migration.** Its first draft stored a digest
   function in `public` whose body named plpgsql_check; PRE-006 refused on it.
   The guard was right. The digest now lives in the harness.
4. **The probe's cron count read NULL on a real `cron.job`** (wrong xpath),
   and the verdict fell through to CLEAR. Fixed, and an unreadable count is now
   its own verdict — `UNKNOWN … do not dispatch` — instead of passing as zero.
5. **The harness first ran the probe with `-c` on one collapsed line**, which
   turned everything after its first `--` comment into a comment. Every
   scenario read `probe=?`. It now runs the probe with `-f`, as the Owner will.
