## Findings for the Auditor (reported, not acted on — none of these is D1's to change)

**F-P1-1 · Presence has no opt-out, and last-seen does.** The existing sync trigger hides `last_active_at` from other
members when `privacy_settings.active_status = 'off'` ("Presence opt-out: 'off' hides active status", in its own
source). `P1-interface.md` §1 (Realtime Presence, `track({ u })` for every signed-in client) says nothing about that
setting. Implemented as written, a member who turned active status off would show a green dot to everyone. The
interface is frozen and the client is D2's; this needs the Auditor to reopen §1 or rule that it is acceptable.

**F-P1-2 · The reservation omits `public.profiles_public_data`.** Every `profiles` UPDATE the two new functions make
also writes that table through the trigger above. It is the same side effect the timer has today, at far lower
volume. It should be on the reservation so no concurrent unit reserves it unaware.

**F-P1-3 · D2's existing test pins the timer.** `src/components/__tests__/AdminUsersActivity.test.ts` asserts that
`useLastActive` writes `last_active_at: new Date().toISOString()` and `last_platform: isNativeCapacitorApp()`. D2's
cut-over has to change that test in the same PR, or the cut-over is red on its own suite.

**F-P1-4 · The new check is RED until D2's cut-over.** `.github/workflows/d1-p1-client-timer.yml` fails on every PR
that touches `src/**` until `useLastActive.ts` stops writing profiles — by design (the gate). It should not be made a
required check before it has gone green once on staging, or it blocks the server half on the client half.

**F-P1-5 · Skill text disagrees with the repository (Standing Rule 21).** The `50mm-developer-1-db-runtime` skill names
staging as `ztzutckwdhetphwghuzj`. `apply-migration.yml` pins staging to `fpszggreishhuvdpkmdr`, which is the project
every staging reading in this project has used. The skill is stale; nothing here used the stale ref.
